# If something breaks

The on-call playbook. Match the symptom on the left to the fix on the right. If you've tried the fix and it didn't work, **don't keep trying** — email ThreadCloud Support at [hello@threadcloud.io](mailto:hello@threadcloud.io).

## Quick triage

| Symptom | What to do |
|---|---|
| Page is blank / 500 error | Refresh once. Then **[restart the worker](#worker-stuck)**. Then email [hello@threadcloud.io](mailto:hello@threadcloud.io). |
| AI classification stuck or not progressing | **[Stop and restart](#classification-stuck)** — see below |
| Label printer not printing | **[Use Shopify Admin fallback](#printer-fallback)** — fully supported |
| Supplier didn't get the email | **[Resend from PO tab](#resend-supplier)** |
| Shopify says "rate limit exceeded" | **Wait 60 seconds and try again.** The worker retries automatically. |
| Image upload failed | Re-upload the same image. If it fails twice, the image is too large — resize to under 4MB and retry. |
| "Missing access token" error | This was a real bug — it's been fixed. If you see it, refresh the page. If still broken after refresh, email [hello@threadcloud.io](mailto:hello@threadcloud.io). |
| Parse times out on a PDF | **[Try Excel](#parse-timeout)** — see below |
| Apply Selected says "0 ready" | Some rows are still <span class="badge badge-warn">NEEDS REVIEW</span>. Filter to "Needs review", fix each, then re-select. |
| Clean Catalog reports no safe fixes | Review the source facts and the Legacy Enrichment queue. Ambiguous or incomplete rows are intentionally review-only; do not force an overwrite. |
| Inventory refresh fails on an untracked variant | **[Inventory snapshot refresh](#inventory-snapshot-refresh)** — the last good snapshot is retained. |
| Historical performance is unavailable | **[Historical ledger access](#historical-ledger-access)** — do not infer history from current stock. |
| Catalog rolled back wrong | **[Undo via Legacy Enrichment](#wrong-rollback)** |
| Order status won't change | Refresh. If still stuck, **[check the supplier ack](#stuck-status)**. |
| Wrong size received | **[Fix size](/workflows/receiving/#fix-a-wrong-size)** on the receiving document. Do not unreceive it first — that hides the button. |
| Fixed a size but the document still shows the old one | Correct and expected. A receiving document is a permanent record of that day, not live stock. Check the order's **Receive** tab instead. |
| Reorder says "Could not verify Shopify cost. Try again." | **[Reorder cost read](#reorder-cost-read)**. Nothing was created; pick again in a moment. |
| Reorder says "Variant costs differ in Shopify. Review them before reordering." | **[Reorder variant costs](#reorder-variant-costs)**. Fix the costs in Shopify first. |
| Reorder product reads "Source cost needed" or "has no supplier cost on file" | **[No supplier cost on file](#no-supplier-cost)**. Enter the cost once, or set it in Shopify. |
| "ThreadCloud could not fill every missing Shopify cost. The reorder was still created." | Informational. The reorder is fine. Set the cost on the product in Shopify when convenient. |
| Reorder PO tab shows "Purchase order not issued" | **[Reorder PO not issued](#reorder-po-not-issued)**. Read the reason under the heading. |
| "Edit product details" says "Product details could not be opened" or "could not be saved" | **[Product repair from Reorder](#product-repair)**. |
| Enrich product reads "Pushed but unverified" | **[Unverified Shopify product](#unverified-product)**. Push the product again to link the named sizes. |
| Enrich product reads "Not pushed" with "pushing again is fenced" | **[Fenced push](#fenced-push)**. Click **Verify with Shopify**. It never creates a product. |
| Enrich Approve landed but a line under it starts with "Approved." | Not an error. The product is approved by you; the engine could not settle it. The line names the reason and the fix. Do what it says, or move on. |
| Enrich bulk buttons are greyed out | A product editor is mid-save or holding a failed save. Finish it or click **Retry saves**, then the bar comes back. |
| Supplier says the link reads "This order needs a corrected PO number" | **[No real PO number](#no-po-number)**. Assign a PO number, re-issue, send the new link. |
| Supplier says the link reads "This purchase order was revised after this link was sent" | You re-issued the PO. Send them the current link from the PO tab. |
| Supplier says the link reads "This order was revised while you were reviewing it" | Nothing on your side. They refresh the page and answer again. |
| Supplier review says "This review moved on. Reloading." | Someone else changed the review at the same time. Let it reload, then continue. |
| Confirmed cost line shows red "currency differs" or "Not applied." | **[Confirmed cost refused](#confirmed-cost-refused)**. |
| Apply product details says "would duplicate another product" | Two products would end up with the same supplier reference. Untick or correct the model and colour codes, then apply again. |

## Worker stuck

If a background process (classification, enrich, push) appears frozen:

<ol class="steps">
  <li>Refresh the page. The worker auto-resumes from where it left off.</li>
  <li>If still stuck, click <strong>Stop</strong> on the workflow surface, wait 5 seconds, then click the run button again.</li>
  <li>If still stuck after 5 minutes, the worker may have hit an external API outage. Wait 15 minutes and retry once.</li>
  <li>If still broken: email <a href="mailto:hello@threadcloud.io">hello@threadcloud.io</a> with a screenshot.</li>
</ol>

## Classification stuck

The progress bar isn't moving and the ETA isn't updating.

<ol class="steps">
  <li>Click <strong>Stop</strong> on the AI Classification step. Wait for it to confirm "Stopping…" → "Run Classification".</li>
  <li>Click <strong>Run Classification</strong> again. The worker picks up only the pending rows.</li>
  <li>If the same row keeps failing, open the error drawer ("View errors" link at the top) — see what it says.</li>
  <li>If it's an Anthropic API error, just keep retrying. The API recovers on its own.</li>
</ol>

<div class="callout callout-info">
<div class="callout-title">Why this matters</div>
The worker is designed to be safe to stop and restart at any point. It only claims rows in <code>pending</code> status, so re-running never duplicates work or wastes an AI call.
</div>

## Printer fallback

The Dymo label printer isn't responding, is out of labels, or jams repeatedly.

<ol class="steps">
  <li>Open Shopify Admin → Products.</li>
  <li>In the search bar, type <code>tag:tc-order-247</code> (replace <code>247</code> with the order ID — find it in the URL of the order page in ThreadCloud, e.g. <code>/app/orders/<strong>247</strong>/receiving</code>).</li>
  <li>Select all rows that need labels. Click <strong>More actions</strong> → <strong>Print barcode labels</strong>.</li>
  <li>Choose your label size (Avery 5160 30-up sheet is the safest), pick the products, hit Print.</li>
</ol>

<div class="callout callout-tip">
<div class="callout-title">Why this works now</div>
ThreadCloud writes the SKU into Shopify's variant <code>barcode</code> field on every push. Shopify Admin reads from that field. So the SKU you'd see on a TC label is exactly what gets printed.
</div>

<div class="callout callout-warn">
<div class="callout-title">Heads up</div>
The Shopify Admin label format isn't identical to TC's Dymo layout (no brand name, no colour name — just barcode + SKU + price). It's a working fallback, not a like-for-like replacement.
</div>

## Resend supplier

The supplier says they didn't get the PO email, or you closed the window before saving.

<ol class="steps">
  <li>Open the order → click the <strong>PO</strong> tab.</li>
  <li>Scroll to the bottom and click <strong>Send to supplier</strong> again. The email re-sends with a fresh token.</li>
  <li>If the supplier already responded on the previous link, the new link supersedes it. Tell the supplier to ignore the old email.</li>
</ol>

## Parse timeout

PDF parsing hangs or shows "Parse failed".

<ol class="steps">
  <li>Try the same file again — once. Transient timeouts happen.</li>
  <li>If it fails twice, ask the supplier for an Excel version of the linesheet. Excel parses much faster and more reliably.</li>
  <li>If neither is available, open the order and click <strong>Add Style</strong> — manually add the rows. Slow but bulletproof.</li>
</ol>

## Wrong rollback

You applied enrichment to a batch and the results are wrong.

<ol class="steps">
  <li>Open <strong>Settings → Legacy Enrichment</strong>.</li>
  <li>Scroll past the workflow to the <strong>Applied</strong> table at the bottom.</li>
  <li>Select the rows you want to undo. Click <strong>Rollback</strong>.</li>
  <li>Confirm. ThreadCloud restores the previous metafield values from the snapshot it took before applying.</li>
</ol>

<div class="callout callout-info">
<div class="callout-title">Why this works</div>
Every Apply step saves a snapshot of the existing values before overwriting. Rollback writes the snapshot back. This works for up to 90 days after the apply.
</div>

## Inventory snapshot refresh

The Inventory Snapshot refresh reads Shopify inventory and rebuilds the snapshot. It does not write
product metafields. Variants with inventory tracking disabled are excluded from physical totals, and
a missing tracking signal for MTO, STOCK, or NOS fails closed so an unknown quantity is not reported
as zero.

<ol class="steps">
  <li>Wait for the refresh to finish and check whether the page retained the last good snapshot.</li>
  <li>Fix the tracking or source issue, then run one refresh.</li>
  <li>If it fails again, stop retrying and record the product or variant id for support. Do not use the resulting total for a buying decision.</li>
</ol>

## Historical ledger access

Historical sales requires the app's Shopify <code>read_all_orders</code> grant. If the page asks for
reauthorization, that is an app permission state, not a calculation to work around. Ask the owner to
reauthorize the staging app, then retry once. Until the ledger is available, historical scorecards
and MTO receipt-backed sell-through remain unavailable; current physical on-hand is not a substitute.

## Reorder cost read

A new reorder takes its cost from Shopify, and refuses to open on an incomplete cost read. "Could not verify Shopify cost. Try again." means Shopify did not answer, or answered with an incomplete read. Nothing was created.

<ol class="steps">
  <li>Wait a moment, then pick the product again.</li>
  <li>If it fails three times in a row, check <a href="https://www.shopify.com/status">status.shopify.com</a>.</li>
  <li>If Shopify is healthy and it still refuses, email <a href="mailto:hello@threadcloud.io">hello@threadcloud.io</a> with the product name. Do not work around it by typing a cost from memory.</li>
</ol>

## Reorder variant costs

"Variant costs differ in Shopify. Review them before reordering." means the sizes of that product carry different costs in Shopify. ThreadCloud will not guess which one is right.

<ol class="steps">
  <li>Open the product in Shopify Admin. Check the cost per item on each variant.</li>
  <li>Set them to the same figure.</li>
  <li>Pick the product again in Reorder.</li>
</ol>

## No supplier cost

The picked card reads <strong>Source cost needed</strong>, or adding the product says it "has no supplier cost on file, and ThreadCloud has no record of buying it."

<ol class="steps">
  <li>From the Reorder search: type the <strong>Unit cost</strong> and its currency, then click <strong>Open reorder</strong>.</li>
  <li>From inside a reorder workspace: set the cost on the product in Shopify (or receive it through ThreadCloud once), then add it.</li>
  <li>A saved list skips these products and names them as "left out". Reorder each on its own from the search.</li>
</ol>

## Reorder PO not issued

The PO tab shows <strong>Purchase order not issued</strong> and a reason. Match it:

| Reason | Fix |
|---|---|
| "There is nothing to send. Complete at least one product before issuing this purchase order." | Go back to Pick (<strong>Edit reorder</strong>) and set at least one size quantity. |
| "This purchase order has already been sent. Open an amendment to revise and re-issue it." | It is issued. To change it, open an amendment, then <strong>Re-issue PO</strong>. |
| "This purchase order cannot be revised because receiving has started." | Expected. Receiving freezes the PO. Place a new reorder for anything extra. |
| "This purchase order was issued by another request. Reload the page to see the current version." | Someone else issued it at the same time. Reload. |
| "N ordered lines cannot be committed" | Those products are missing a fact the supplier needs. <strong>Edit reorder</strong> and fill it in. |

## Product repair

<strong>Edit product details</strong> on a reorder line opens the product in Catalog Repair. "Product details could not be opened" or "Product details could not be saved" means that hand-off failed.

<ol class="steps">
  <li>Try once more.</li>
  <li>If a field shows <strong>Edit not saved</strong>, re-enter it. The save refuses until every unsaved field is entered again ("Re-enter the unsaved details before saving this product.").</li>
  <li>If a repair failed earlier, Settings → Legacy Enrichment lists it with a <strong>Retry repair</strong> button.</li>
  <li>Still failing: email <a href="mailto:hello@threadcloud.io">hello@threadcloud.io</a> with the product name.</li>
</ol>

## Unverified product

An Enrich product reads <strong>Pushed but unverified</strong>. Shopify has the product, but at least one ordered size is not linked to a variant. Receiving cannot book that size.

<ol class="steps">
  <li>Read the line. It names the sizes.</li>
  <li>Click <strong>Push update</strong> on that product (or <strong>Push selected</strong> on several). The push links the missing sizes.</li>
  <li>It should now read <strong>Pushed and verified</strong>. If the line reads "This product exists in Shopify. Add sizes before receiving." the product has no ordered sizes: add them in Build Order.</li>
</ol>

## Fenced push

An Enrich product reads <strong>Not pushed</strong> with "A previous push did not record a product identity, so pushing again is fenced." A push may have created the product, but ThreadCloud never got the id back. Pushing again could create a duplicate, so it is blocked.

<ol class="steps">
  <li>Click <strong>Verify with Shopify</strong> on that product. It asks Shopify what it has and links it. It never creates a product.</li>
  <li>If it finds one, the line reads "Found this style's existing Shopify product by SKU and linked it. No product was created." Carry on.</li>
  <li>If it finds nothing, the error shows under the button. Check Shopify Admin for a draft with the product's SKU. If there is none, email <a href="mailto:hello@threadcloud.io">hello@threadcloud.io</a> before pushing again.</li>
</ol>

## No PO number

The supplier opens the acknowledgement link and sees "This order needs a corrected PO number. Please ask the buyer to issue a corrected purchase order and acknowledgement link." The order has no real PO number, so nothing can be acknowledged against it. This happens on older orders that were sent before PO numbers were assigned.

<ol class="steps">
  <li>Open the order. If the PO tab says "This legacy order has no purchase order number. Assign one before issuing it.", assign one.</li>
  <li>Re-issue the PO.</li>
  <li>Send the supplier the new link (<strong>Email brand contact</strong> or <strong>Supplier ack link</strong>).</li>
</ol>

## Confirmed cost refused

On the supplier review, a ticked cost came back red instead of green.

| Line reads | Meaning | Fix |
|---|---|---|
| "currency differs" beside the line | The confirmation states the cost in a currency other than the order's. It is refused, not converted. | Check the document. If the supplier really changed currency, that is a conversation with them, not a tick. |
| Refusal naming a changed order cost | The order's cost moved after you opened the review (someone edited it in Build). | Reload the review and tick again against the current figure. |
| "Not applied." with no reason | The apply did not reach that line. | Reload and apply again. If it repeats, email <a href="mailto:hello@threadcloud.io">hello@threadcloud.io</a>. |

## Stuck status

An order is stuck at "Sent to supplier" forever.

<ol class="steps">
  <li>Check if the supplier has responded — open the order → PO tab → look for the supplier ack timestamp.</li>
  <li>If they have responded, the page may need a refresh. Press <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> (hard refresh).</li>
  <li>If they haven't, click <strong>Approve as-is</strong> on the PO tab — this skips the supplier loop and marks the order confirmed manually.</li>
</ol>

## Big-picture failures

These are the rare ones. If you see one of these, **email ThreadCloud Support immediately** at [hello@threadcloud.io](mailto:hello@threadcloud.io) — don't try to fix them yourself.

| Symptom | What it means |
|---|---|
| Every page across the app is 500 | Production deploy is broken. Possibly a Fly.io outage or a bad merge to main. ThreadCloud Support handles this. |
| All Anthropic calls failing for 30+ min | Anthropic API outage. Status: [status.anthropic.com](https://status.anthropic.com). Nothing to do except wait. |
| Shopify Admin won't load at all | Shopify outage. Status: [status.shopify.com](https://www.shopify.com/status). Wait. |
| Bank-side currency feed says the wrong rate | The multi-provider FX fallback should catch this. If somehow all three providers are wrong, set the FX manually on the order (Receiving tab) and email [hello@threadcloud.io](mailto:hello@threadcloud.io). |
| A push wrote products with bad data | Don't panic. Pull them back: Shopify Admin → filter by `tag:tc-order-{id}` → bulk-delete. Then re-push from ThreadCloud after fixing the source. |

## What only the Owner should do

- Approve a push of more than 200 products at once
- Edit the AI prompts (Settings → AI & Models)
- Change the metafield namespace or schema
- Use the dev tools page (`/app/settings/dev`)

These are platform-level operations and only ThreadCloud Support should handle them:

- Run direct database operations
- Merge code to `main` (production)
- Manual `fly deploy` to recover a broken production deploy

If your fingers are hovering over any of those, stop and ask.
